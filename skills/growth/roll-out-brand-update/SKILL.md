# Roll Out Brand Update

Use the user's existing project context, policies and tools. Ask only for missing information that materially changes the result. Accept authorized exports when live integrations are unavailable; distinguish unavailable evidence from negative evidence. Follow the requested depth: discussion and audit do not authorize implementation or external actions. Keep project-specific data in the project rather than this public skill.

At invocation, read [the corrective-feedback loop](references/feedback-loop.md) and [regression cases](references/regression-cases.md). Apply learned corrections below before choosing an approach.

## Workflow

1. Locate approved brand decisions and inventory requested touchpoints with owner, source, current state and target state. Distinguish identity changes, content corrections and functional changes.

2. Map reusable tokens, artwork, typography, domains, app/store links and credits. Preserve commissioned assets and legal attribution; do not replace product-state semantics with decorative brand colors.

3. Prepare scoped changes following each repository or service’s release path. Check whether copied assets and remote templates must be updated independently.

4. Inspect rendered mobile, desktop, email and document outputs as applicable. Search for old domains and assets but classify legitimate historical references before replacing them.

5. Verify forms, deep links, checkout, downloads, consent and analytics still work. Record drafts, deployed changes and remaining surfaces separately. Do not declare the rollout complete from a single homepage screenshot.

## Deliverable

Touchpoint checklist, approved changes, render evidence and release status by surface.

## Example request

> Use $roll-out-brand-update: Roll out our new brand across the app, site, emails and downloadable resources.

## Learned corrections

When corrective feedback follows this skill, update the relevant instruction and its regression case in the same turn using the linked loop. Keep project-only values in private project context; keep this section limited to reusable decision rules.
